Library & File Plan Manager v2.2

SharePoint permissions map (file-plan style, grouped by team) + an admin screen that creates document libraries correctly and registers them automatically, so nothing gets forgotten again.

Built 11 Aug 2026 12:30 BST

First screen is live below (File Plan browse). Still to come: Admin: Create Library (with a bulk queue), the permissions view/add/remove screen, and whole-site search by SG/DG group name — that last one needs a new "permission index" flow, not built yet.

Before You Start

  1. Create the LibraryFilePlan SharePoint list below (all columns, exact names, no spaces).
  2. Import the Create Library (App) flow package (download below) via Power Automate → Import → Import Package (Legacy).
  3. Test the flow manually before touching Power Apps at all — see the Testing section below.
  4. Once both are confirmed working, the Power App screens (Browse/File-plan, Search, Admin: Create Library) get built and added here.

Backfill Existing Libraries

LibraryFilePlan only tracks libraries created after this system existed — it starts empty, and won't have your existing ~500 libraries in it. This flow fixes that in one run: it scans every real document library on the site (skipping SharePoint's own system libraries — Site Assets, Style Library, Form Templates, Preservation Hold Library, and a few others), and for anything not already in LibraryFilePlan, adds a row with:

  • LibraryUrl, DisplayName, Title, SiteUrl — filled in automatically, read straight off the real library
  • IsLimited — guessed automatically: true if the library already has broken permission inheritance (HasUniqueRoleAssignments), false if it's still inheriting normally. Since every Limited library your other flow creates breaks inheritance and every Normal one doesn't, this should be right for anything created by this system already — for libraries created some other way in the past, spot-check a few after running
  • Team, SubTeam — left blank. Only you know which team actually owns which library, so this is the one part left for you to fill in by hand, directly in the SharePoint list view (which supports quick-edit/grid view for fast bulk filling — much faster than opening each row individually)

Safe to run more than once — it checks each library's LibraryUrl against what's already tracked first, so it only adds what's missing, never duplicates.

This scans your whole library list — with ~500 libraries, expect this to take several minutes to run. It runs 20 libraries at a time in parallel (not one at a time) to keep this reasonable, but a whole-site scan is still a whole-site scan. Let it finish; don't re-run it while it's still going.
Import via Power Automate → My flows → Import → Import Package (Legacy), same as the other flow. Test → Manually, leave Site URL blank (defaults to the main site), Test. Once it's done, open LibraryFilePlan in SharePoint, switch to grid/quick-edit view, and fill in Team (and SubTeam where relevant) for every row.

Rebuild Permission Index

Power Apps can't read SharePoint permissions directly (confirmed early on in this project — the standard connector only exposes list items, never role assignments), and a search screen can't afford to live-query every library's permissions on every keystroke. This flow bridges that: it scans permissions once and writes a flat, fast-searchable copy into PermissionIndex. The eventual group-search screen just filters that list — instant, no live SharePoint calls per search.

Scoping decision worth knowing: this only scans libraries that already have broken/unique permissions (HasUniqueRoleAssignments = true) — in practice, mostly your Limited libraries. Normal libraries all inherit the exact same site-wide permissions as each other, so indexing each one individually would just be ~460+ duplicate rows saying the same thing. Anything not in the index after a rebuild simply means "inherits the site's normal permissions" — worth stating that plainly wherever the search results eventually get shown.

For each in-scope library, per group/user with direct access, it writes one row. If that group is a native SharePoint Group (like SG_Cadets-Admin-Ltd_MEM), it also looks one level inside that group's own membership — this is how a nested DG_... AD group shows up in the index too, tagged via NestedUnderGroup, without needing Microsoft Graph or an Azure AD app registration (confirmed early in this project that Graph is off the table here — this works because SharePoint's own REST API can list a native group's members, and a nested AD group appears in that list as an entry, even though expanding that group's own members would need Graph, which this doesn't do).

This flow deletes the entire contents of PermissionIndex and rebuilds it from scratch every time it runs — that's intentional (avoids stale/duplicate rows), but don't manually add anything to that list expecting it to survive a rebuild.
Import via Power Automate → My flows → Import → Import Package (Legacy). Test → Manually, leave Site URL blank. Given this only scans unique-permission libraries (a small subset of the ~500 total), expect this to run noticeably faster than the Backfill flow. Once it's done, open PermissionIndex in SharePoint and spot-check a few rows against what you already know about a couple of Limited libraries' real permissions.
Not wired to anything in Power Apps yet — the group-search screen that reads this list hasn't been built. Re-run this flow manually whenever the index needs refreshing (after creating/editing Limited library permissions); a scheduled/automatic rebuild is a future nice-to-have, not built now.

What the flow does

Triggered from Power Apps (or manually, for testing). Per library:

  1. Creates the library (BaseTemplate 101, EnableFolderCreation: false) using the technical name, with the correct sensitivity label depending on Normal vs Limited
  2. Adds a CAT choice column (fill-in-your-own enabled, "Please select or create a category for these documents." default prompt)
  3. Adds a Status choice column: Draft / Under Review / Reviewed / Published / Final / Superseded / Expired
  4. Creates WiP view (default) — items without a retention label, grouped by CAT
  5. Creates Records view — items with a retention label, grouped by CAT
  6. Renames the library's Title to the pretty display name
  7. If Limited: breaks role inheritance completely (clean slate, nothing carried over from the parent site), grants SG_Cadets-Admin-Ltd_MEM and SG_IHUB Full Control automatically (fixed, nothing to fill in — see below), then removes the flow-runner's own account (SharePoint auto-adds whoever breaks inheritance, as a lockout safety net — the flow strips that back out so only the two intended groups remain)
  8. Registers the new library into LibraryFilePlan automatically

Known Import Bug — Fix Before Testing

If you test the flow and get Action 'Select_Categories' failed... The template language function 'createArray' expects a comma separated list of parameters. The function was invoked with no parameters. — this is a known bug in the imported flow, not something you did wrong. Fix the action below before testing (or re-download the flow package above, which already has this fixed).

In the flow designer: Edit the flow, click the Select_Categories action to expand it, click into its From box, select all and delete, then copy/paste the box below in as the replacement. Save the flow after.

Select_Categories — From

if(empty(trim(coalesce(triggerBody()?['Categories'], ''))), json('[]'), split(triggerBody()?['Categories'], '\n'))
The flow used createArray() with no arguments to mean "empty array" when Categories is left blank, which isn't valid syntax. json('[]') is the correct way to write an empty array.

If you already pasted an earlier version of this and got Action 'Create_FilePlan_Row' failed: Invalid JSON. A token was not recognized. — that's a real Power Automate quirk: interpolating a boolean with @{triggerBody()?['IsLimited']} renders as True/False (capital, .NET-style), which isn't valid JSON. JSON needs lowercase true/false. The block above already has the fix — re-paste it in.

Limited Libraries — Two Fixed Groups, Nothing to Fill In

For a Limited library, the real-world sequence is: create the library locked down first, then email another team to get the actual access group created and added later. If Break_Role_Inheritance strips every permission with nothing left behind, nobody — including you — can get back in to add that group when it's ready.

Since that other team owns every group that ever gets added, there's no field for it on this form at all — nothing to type, nothing to get wrong. Every Limited library automatically gets exactly these two groups at Full Control, and nothing else:

  • SG_Cadets-Admin-Ltd_MEM — Full Control
  • SG_IHUB — Full Control

This isn't an "invert and remove the rest" — copyroleassignments=false already means nothing is inherited or copied in the first place, so there's nothing to enumerate or strip. The flow just grants these two straight after breaking inheritance. When the other team's group is ready, it gets added by hand in Library Settings → Permissions — that's a deliberate manual step owned by them, not something this flow does.

One more wrinkle found during testing: SharePoint automatically adds whoever's account calls breakroleinheritance — in this case the flow's own connection identity — as a direct user with Full Control, as a built-in lockout safety net. That leaves a third, unwanted entry in the permissions list on top of the two SG groups. The flow now removes that automatic grant as its last step, so the final permissions list is exactly the two SG groups and nothing else.

This changed which actions exist inside the flow, not just one field's content — it can't be patched by editing a single expression box like the fix above. Delete the flow you already imported and re-import the updated package from the download link at the top of this page, then redo both tests from scratch.

Site URL Now Defaults

Every test so far has been on the same site, so Site URL now has a default (https://modgovuk.sharepoint.com/teams/1598) — the Power App's future call to this flow can skip it entirely and this fallback fills it in.

Trigger schema changes (adding a default value, changing what's required) can't be hand-edited at all — the trigger's Code view is read-only, and its Parameters tab won't show inputs correctly for a flow whose trigger was originally hand-authored as raw JSON rather than built click-by-click in the designer. This one needs the delete + re-import below, same as the other structural changes.
The trigger's own "default" only applies when a real Power Apps call omits the field entirely — Power Automate's manual Test panel does not honour it; leaving Site URL blank in Test sends an empty value and every action fails with dataset ... may not be null or empty. So every action's dataset now falls back to the main site directly via coalesce(), which works in both Test and real Power Apps calls. Still type the Site URL in Test if you want to be explicit about it — it's optional now, not broken if left blank.

Building the Power App

Create a new blank canvas app in Power Apps Studio, then follow these steps in order.

1. Data connections

Data panel → Add data → add these before pasting any screen YAML:

'LibraryFilePlan'          (SharePoint → your main site → LibraryFilePlan)
'Create Library (App)'     (search Power Automate flows in Add data → this is the flow you already imported and tested)
Adding the flow as a data source is what makes 'Create Library (App)'.Run(...) available to call from the Admin screen — without this step, the Run Queue button won't find the flow.

2. App.OnStart

Select the App object (top of the tree, not any screen) → OnStart property → paste this in full, replacing whatever's there:

Set(varTenantHost, "https://modgovuk.sharepoint.com");
ClearCollect(colFilePlan, 'LibraryFilePlan');
ClearCollect(
    colFilePlanFiltered,
    AddColumns(colFilePlan, TeamName, Team.Value, SubTeamName, Coalesce(SubTeam.Value, ""))
);
ClearCollect(
    colTeamGroups,
    Sort(
        AddColumns(
            GroupBy(colFilePlanFiltered, TeamName, GroupedItems),
            ItemCount, CountRows(GroupedItems)
        ),
        TeamName,
        SortOrder.Ascending
    )
);
Clear(colFlatSource);
Collect(colFlatSource, AddColumns(colTeamGroups, RowType, "Team", SortKey, TeamName, RankInGroup, 0));
Collect(colFlatSource, AddColumns(colFilePlanFiltered, RowType, "Library", SortKey, TeamName, RankInGroup, 1));
ClearCollect(colExpandedKeys, Filter(Table({TeamName: "seed"}), false));
Set(varIsAdmin, Lower(User().Email) in ["allan.hamilton775@mod.gov.uk", "dan.smith391@mod.gov.uk"]);
ClearCollect(colQueue, Filter(Table({TechnicalName: "seed", DisplayName: "", Team: "", SubTeam: "", IsLimited: false, Categories: ""}), false));
Set(varQueueRunning, false);
Set(varQueueTotal, 0);
Set(varQueueDone, 0)
This loads the library list once at app start and builds the initial grouped-by-team view. The File Plan screen's search box rebuilds all four collections itself as you type — App.OnStart just needs to set them up once so the screen isn't blank before you've typed anything. varIsAdmin gates the Admin screen — edit the email list directly in this line if who's authorized ever changes.

Sub-Team is a free-text box here rather than a suggestion dropdown — Modern Combobox has a known Microsoft-acknowledged instability issue (documented in this Bible's known-bad-patterns.md) that wasn't worth risking on a field that's meant to allow new values anyway. The queue is entirely local (a Power Apps collection) until you hit Run — closing the app before running loses whatever's queued, nothing's written to SharePoint until then.
v2.0 is a full rebuild of the accordion mechanism, not a patch — delete the whole scrFilePlan screen and paste fresh into a new blank one, and re-paste App.OnStart in full (it now builds a fourth collection, colFlatSource). If you already have v2.0 pasted, v2.1's changes are additive (new Clear button, existing controls' properties updated) so pasting v2.1 over the top should be fine.
v1.x used nested galleries (a Team gallery containing a Library gallery per row) with dynamically computed row heights, switching the outer gallery's Variant between Vertical and VariableHeight trying to get it to reflow correctly — it never did; expanding a Team just overlapped the rows below it. v2.0 throws that out and uses the pattern your own sidebar.md component (powerappsui.com) actually uses for its parent/child tree: one single flat gallery, every row the same fixed height, no nesting at all. A Team being "expanded" doesn't resize anything — it just changes which rows are included in the gallery's own Items formula (Filter(colFlatSource, RowType = "Team" || TeamName in colExpandedKeys.TeamName)). Since every visible row is the same height, the gallery reflows correctly by default — there's no per-row height math left to get wrong.
v2.1: added a Clear (✕) button next to the search box, and the result count line now reads "Showing N libraries..." in purple/bold while a search is active, vs "All libraries — N..." in grey when it's blank — so it's visibly obvious the search actually did something.
On this screen, search is instant and local — it's filtering the LibraryFilePlan list already loaded into the app, no network call, so there's deliberately no spinner (there's nothing to wait for). Typing a matching term also auto-expands every Team that has a result, so you don't have to manually open teams to see what matched. Searching by SG_/DG_ permission group name across the whole site is a separate, not-yet-built screen — that one genuinely hits SharePoint live and will need a spinner, once the permission-index flow exists.
v1.2 fix: Copy() actually takes a plain text value directly — Copy(varTenantHost & ThisItem.LibraryUrl) — not a control reference. The v1.1 attempt (Copy(txtClipboardStaging)) errored with Expecting a Text value instead, which meant the whole hidden off-screen Classic/TextInput workaround wasn't needed at all — removed it, the Copy link button is now a single line.
